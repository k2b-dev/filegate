# S3 compatibility

The S3-compatible listener is for tools that can speak path-style S3 but should store bytes on Filegate mounts.

## Enable S3

```yaml
version: 1
config:
  s3:
    enabled: true
    listen: ":9100"
    region: us-east-1
```

Seed the first credential in the bootstrap file, apply the manifest, and restart:

```sh
sudo fg config s3 key add --config /etc/filegate/conf.yaml \
  --all-buckets

fg config apply -f filegate.manifest.yaml --config /etc/filegate/conf.yaml
sudo systemctl restart filegate
```

The key command prints the generated access key and secret key once. Store them as secrets.

`s3.enabled` and `s3.listen` are static: the listener is bound at startup, so enabling S3 needs a restart. Access keys are not — see below.

## Bucket model

| S3 concept | Filegate concept | Scope |
|---|---|---:|
| Bucket | Configured storage mount basename | Per mount |
| Object key | File path inside a mount | Per object |
| Multipart upload | Mount-local staging under `.fg-uploads` | Per upload |
| Access key | S3 credential entry in config | Per key |
| Bucket allowlist | `s3.keys[].buckets` | Per key |

CreateBucket and DeleteBucket are rejected. Operators create buckets by configuring mounts.

## Client example

```sh
aws --endpoint-url http://127.0.0.1:9100 s3 ls s3://data/
```

Use path-style addressing. Configure the client endpoint to the S3 listener, not the REST listener.

## Multi-tenant keys

| Field | Scope | Meaning |
|---|---:|---|
| `access_key` | S3 key | SigV4 access key ID. Generated when omitted. |
| `secret_key` | S3 key | SigV4 secret. Generated when omitted, shown once. |
| `buckets` | S3 key | Allowed bucket names. `*` grants every configured mount. Empty grants none. |
| `requests_per_second` | S3 key | Sustained request rate limit. `0` means unlimited. |
| `burst` | S3 key | Burst size. Defaults to RPS when unset. |

Requests to buckets outside the key allowlist return AccessDenied without revealing bucket existence.

## Managing keys at runtime

Access keys are runtime resources, not static configuration. They live in the runtime config store and can be created, relabelled, rate limited, rotated and deleted while the service runs — from the admin S3 page or the `/v1/s3/keys` routes. A new or rotated secret is shown once at creation and never again.

Keys written into the config file or the environment are **seeded, not synchronized**. They are imported the first time the service starts against an empty runtime store; after that the store owns them, and configured keys are logged and ignored. A key deleted in the admin UI therefore stays deleted across restarts rather than being recreated by the file that first introduced it.

Deleting the last key is allowed and means exactly what it says: nothing can authenticate against the S3 listener until another key exists.

## Supported operation groups

| Group | Scope | Notes |
|---|---:|---|
| Bucket listing | S3 listener | ListBuckets is filtered by key allowlist. |
| Object read/write/delete | Bucket object | Uses Filegate filesystem storage and metadata index. |
| Multipart upload | Bucket object | Parts are staged under `.fg-uploads` and completed atomically. |
| CopyObject | Bucket object | Uses Filegate copy behavior. |
| DeleteObjects | Bucket object set | Batch delete support. |

See [S3 reference](/docs/en/reference/s3) for supported operations and deviations. The
deep references cover the [HTTP surface](/docs/en/reference/s3-api), [configuration and
credentials](/docs/en/reference/s3-config), and [client setup](/docs/en/reference/s3-clients).
